You are building **Token for Granted**, a static web app that is a navigation-and-education site for a university researcher, a research office or a non-profit that wants grant money in the United States, with an opportunity search built in. You are the build-and-delivery role; the content has already been researched and sits in `content-pack/`. **The wordmark is "Token for Granted"** (not "Token for Granted Explorer").

## 1. Hard rules

- **Never invent content.** Definitions, summaries, explanations, figures, thresholds, dates, dollar amounts, deadlines, the meaning of a status or a code — all come from `content-pack/` or, on `/find` and `/funded`, from the public data named in §4c, shown as that data. If something is missing, render an amber `TODO(author)` marker (`.bx-todo`) and list it on `/methods`. Do not fill gaps from your own knowledge. Grant rules changed a great deal in 2025 and 2026 and you do not know the current ones.
- **Body text is rendered as written.** Structure it, link it — never rewrite or paraphrase `review.md`, a record's `what`, a glossary definition or any other pack prose.
- **Uncited prose fails the build.** Any block of ≥ 25 words in `review.md` or in a primer body with no `[n]` and no `<!-- framing -->` marker (immediately before it, immediately after it on the next line, or inside the block) is a content-build error (APP-SPEC §6.1). List it in `BUILD-ERRORS.md` and surface it on `/methods`. **Do not fix it by adding a citation.** Record prose in the extension files and glossary definitions are cited the same way and count as citing text: a reference cited only from a record or a glossary entry is in use (`used_by` on the reference says where).
- **`<!-- synthesis -->` passages stay visible.** In this pack the marker sits at the end of the synthesised sentence, inside a paragraph (35 of them). Render the sentence with a quiet underline or left rule and a "synthesis" label, give each an id, and link every one from `/methods`. Never strip the marker.
- **Nothing implies peer review, official status, or advice.** `manifest.venue` and `manifest.disclaimer` say what this is; render the disclaimer in the footer of every page and in full on `/about`. `as_of` appears on `/`, `/read` and `/about`, and every record page shows its own `as_of`. No page tells a reader what to do about their own application ("the notice requires…" is fine; "you should…" is not); if pack text does, it is a pack error — record it on `/methods`, do not render it changed. `consolidation-report.json` lists the records known to carry a second-person sentence.
- **No institution is tailored for.** There is no account, no server-side state, no analytics beacon, no example university or non-profit, and no invented example anywhere in the UI. Personalisation (pathfinder answers, saved filters, the notepad) lives in `localStorage` only, with a visible "stays in this browser" note. The things that do leave the browser are stated plainly where they happen: `/funded` queries the USAspending API and the NSF Awards API live, and `/find` loads this site's own harvested data files.
- **Status is a reading on one day.** Every programme carries `status` and the date it was read (`status_as_of`, else `as_of`). Show the two together, always, in the pack's words for each label (the glossary entry `status-label` and the primer `reading-a-funding-notice` define them). Never write "open now". Harvested Grants.gov data may sit *beside* a pack status (§4b) and never replaces it.
- **Law in motion.** A change record's `status` (proposed, announced, enacted, final, pending-implementation, enjoined, vacated, in-litigation, on-appeal, rescinded, frozen-by-appropriations) renders as a labelled chip with its date wherever the record appears. `pending_changes[]` on any record renders as a labelled block. A budget request is labelled a request. Where a record says an order covers named plaintiffs or certain states, that sentence is never truncated.
- **Where sources disagree, show both.** A record's `conflicts` list renders as a block labelled "Where sources differ"; `variants` (other wordings of the same record met in another sweep slice) render under a closed disclosure labelled "Also recorded". Never pick one silently.
- **The recheck is visible.** On a reference card each key fact shows its `fact_check` code in words (C confirmed on the live page · S stated in part · N not found on the second reading · X the page says otherwise · - not re-read), `rechecked` and `recheck_result` (page re-read, re-read in part, or could not be re-read), and a quiet flag when `recheck` is true.
- **No recommendations.** No route, programme, funder, paid database, consultant or grant writer is recommended, scored or ranked beyond the pathfinder's count (§4b) and the user's own filters. Success rates are shown with source and fiscal year, never as odds.
- **No runtime fetches of pack content.** Everything in `content-pack/` ships in `dist/`. The only runtime network calls are those named above.
- **Fail loudly in the content build.** Schema violation, unresolved `[n]`, unknown term/concept/route/gate/programme/funder/standing/mechanic/help/change id, missing data file, ambiguous term variant → non-zero exit with a clear list. Do not "fix" the pack silently; write `content-pack/BUILD-ERRORS.md` and continue building the app with whatever validated (the errors also surface on `/methods`).
- **Delivery mode is `pages`** and it is not yours to change. The app ends up public — see §6b.
- **GitHub identity:** `danieladamek`. Verify with `gh auth status` before any push. **The repo already exists** at `github.com/danieladamek/token-for-granted` with the content pack and a probe workflow; do not `gh repo create`. The local branch is ahead of the remote; pull, then push.
- Vault contract: don't touch anything outside this folder except the K9 item's `state` in `../../notes/Backlog/`; leave a scrum note at `notes/Scrums/YYMMDD.md` in the exact format from `../../../CLAUDE.md` (with the `app:` key above). Never edit `content-pack/`, `source/`, `docs/`, or the hub note.

A second tab, **the foundation directory**, searches the private foundations in the IRS exempt-organisation master file (§4c) by name, state, asset size and category, each linking to its ProPublica profile, and says what the directory is (every private foundation the IRS lists, with the IRS's own figures) and is not (it does not show whether a foundation takes requests; community foundations are public charities and are not separable in this file).
- **`/funded` — who has won.** Live queries, stated as such on the page. *USAspending* (`api.usaspending.gov`, no key, CORS open as probed): input an Assistance Listing number (pre-filled from a programme page), optional state, a date window defaulting to the last 12 months, and recipient type (`higher_education`, `private_institution_of_higher_education`, `nonprofit`); show top recipients by obligation (`/api/v2/search/spending_by_category/recipient/` with `award_type_codes` 02–05 and `program_numbers`) and the award count, each recipient linking to its USAspending profile. *NSF* (`api.nsf.gov/services/v1/awards.json`, CORS open to the Pages origin as probed): keyword or programme name, showing awardee, title, amount and dates, linking to the NSF award page. *NIH*: RePORTER refuses a browser's preflight, so the page links to RePORTER with the activity code or opportunity number in the link and says why it is a link. *Foundations*: links to the foundation's own grants database and its ProPublica filing. Cache responses in `sessionStorage`; handle a failed request with a plain message and the manual link. State that these queries leave the browser and go to USAspending or NSF and that nothing else is sent.

### What these surfaces must not do

- No route, programme or funder is ever recommended, scored beyond the pathfinder's count, or ranked by anything but that rule and the user's filters.
- No text tells a reader what to do; records state what rules require and what pages say.
- No harvested status overwrites a pack status.
- No institution-specific content, example applicant, or invented example anywhere in the UI.
- No harvested data is committed to git; it is built into the deployment (§4c).

## 4c. The harvest and the workflows

Two probe runs settled what the sources allow (`source/probe-2026-10-04.json`, `source/probe-2026-10-05.json`): a page cannot query Grants.gov or NIH RePORTER (the browser preflight is refused) and cannot query ProPublica (no permission header; terms forbid redistribution), so everything about open opportunities and about foundations is harvested at night and served as files, and only USAspending and the NSF Awards API are called live.

- **`scripts/harvest/grants-extract.mjs` — the main feed.** Find the newest `https://prod-grants-gov-chatbot.s3.amazonaws.com/extracts/GrantsDBExtract<YYYYMMDD>v2.zip` among the last four days (HEAD each; the day's file was up by 08:44 UTC on the probe days, 78 MB). Download it, stream-unzip and stream-parse the XML; never load it whole. **Read the element names from the file itself** (and from the XSD that Grants.gov links from its XML extract page) before writing the mapping; do not assume them, and write the element names found to `public/data/opportunities/schema-seen.json`. Keep posted notices whose close date is empty or not earlier than yesterday, and every forecast. Write slim records: id, opportunity number, title, agency code and name, status (posted | forecast), post date, close date, last updated, estimated post and due dates for forecasts, applicant-type codes, the free-text eligibility note (first 300 characters), funding instrument, funding category, Assistance Listing numbers, award ceiling and floor, estimated total funding, expected number of awards, cost-sharing flag, description excerpt (first 400 characters), link (`https://www.grants.gov/search-results-detail/<id>`). Shard by top-level agency into `public/data/opportunities/grants/<agency>.json` plus `index.json` (counts by status, by agency, by applicant type; harvest time; the extract's file name and Last-Modified). Target ≤ 1.5 MB per shard before compression; split a large agency by sub-agency if needed.
- **Cross-check, same script:** `POST https://api.grants.gov/v1/api/search2` with `{ keyword: "", oppStatuses: "posted|forecasted", rows: 1 }` for the total and once per applicant type the page pre-sets (`eligibilities` 06, 20, 12, 13); record the API's counts beside the extract's in the manifest. A difference of more than 5 percent is reported in the manifest and on `/find`, not fatal. Take the applicant-type labels from the extract or from one `fetchOpportunity` response; the probe confirmed the labels for 06, 12 and 13 and saw 20 by count only.
- **`scripts/harvest/irs-bmf.mjs` — the foundation directory.** Stream the IRS exempt-organisation master file state files (`https://www.irs.gov/pub/irs-soi/eo_<state>.csv`, lower-case postal code, for the 50 states, `dc` and `pr`; a missing file is recorded and skipped). Keep the rows the IRS's own documentation of the `FOUNDATION` column labels as private foundations (operating and non-operating). **Fetch that documentation at harvest time** (the EO BMF information sheet linked from the IRS's "Exempt Organizations Business Master File Extract" page), take the code labels from it word for word into the manifest, and cite its URL on the directory page; if it cannot be fetched, keep the rows whose `PF_FILING_REQ_CD` is non-zero, show codes as raw codes, and say so. Slim fields: EIN, name, city, state, foundation code, ruling date, asset amount, income amount, tax period, NTEE code. Shard by state into `public/data/foundations/<state>.json`, plus `top.json` (the 500 largest by asset amount) and `index.json` (counts by state, harvest time, source URLs). The page loads `top.json` first and a state shard on demand.
- **`scripts/harvest/irs-990-index.mjs` — optional, non-fatal.** Stream `https://apps.irs.gov/pub/epostcard/990/xml/<year>/index_<year>.csv` (54 MB; it ignores range requests) and, for EINs in the directory, record the latest `990PF` row's tax period and submission date so that a directory row can say when the foundation last e-filed. Do not download or parse the filings themselves: that harvest is unprobed and is a backlog item, not part of this build.
- **`scripts/harvest/federal-register.mjs` and `nsf-rss.mjs` — small, non-fatal.** The newest 200 Federal Register notices matching "notice of funding opportunity" (title, agencies, publication date, URL) and the NSF funding RSS items, shown as two short "recently published" lists under `/find`, each linking out.
- **All harvesters** write into `public/data/` and fold into one `public/data/manifest.json` (`harvestedAt`, counts, source URLs, failures). A failed source exits non-zero **but** leaves the other sources' output in place; the app reads `failures` and says which feed is stale.
- **`.github/workflows/deploy.yml`:** `npm ci → npm test → npm run build:content → npm run harvest → npm run build` (with `BASE_PATH=/token-for-granted/`) → copy `dist/index.html` → `dist/404.html` → `actions/upload-pages-artifact` → `actions/deploy-pages`. Triggers: push to `main`, `workflow_dispatch`, and `schedule: cron "43 9 * * *"` (daily, after the day's extract is up; the schedule run only re-harvests and redeploys). The harvest output is **never committed**; `public/data/` is in `.gitignore`. Use the same action major versions FAR Out's `deploy.yml` uses today.
- **`.github/workflows/probe-sources.yml` and `scripts/probe-sources.mjs`:** keep; they already exit non-zero when a required probe fails. Do not change which probes are required.
- **Local builds** (`npm run build` on Daniel's machine) must not require the harvest: `npm run harvest` is a separate script, and `/find` degrades as described in §4b when the data folder is absent. `scripts/harvest/make-fixture.mjs` (as in FAR Out) writes a small fixture for tests.
